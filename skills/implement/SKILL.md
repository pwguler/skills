---
name: implement
description: "Implement a settled plan test-first, smallest slice at a time. Use when starting implementation of a feature or fix after the plan is settled, or when user says \"implement this\" or \"build it\"."
---

Work the plan one thin slice at a time; a slice is the smallest piece that changes observable behavior. When a spec exists at `docs/specs/<slug>.md`, its acceptance criteria are the plan, worked criterion by criterion, and its non-goals fence every diff. A spec that still has an `## Open decisions` section is a draft: route it back to `drill`.

1. Open a `todo` list before the first test: one item per acceptance criterion when a spec exists, one per slice otherwise, then `verify`, then `rubric` when the work is a UI, a public interface, a name, or a doc. A list of fewer than three items is not opened. Mark each item done as it lands; a skipped item is marked `completed` with `skip: <reason>` added to its subject, and a criterion is never skipped, only left open.
2. Pick the smallest unfinished slice and work steps 3 to 7 on it in this session. When the user asked to hand slices off, a `worker` subagent launched with `skill: "implement"` works steps 3 to 5 on one slice; read its diff, then run steps 6 and 7 here.
3. Write the test that fails for it, through the interface, never against implementation details. If no failing test can be written, the seam is wrong: fix the plan, not the test.
4. Write the minimum code that makes it pass.
5. Refactor only with tests green, in the style of the surrounding code.
6. When the slice's diff deletes or renames a symbol other code uses, or changes a contract another module, a stored record, or an outside caller relies on, run [blast-radius.md](references/blast-radius.md) before the gate.
7. Gate the slice through `verify` and commit on its record.
8. Repeat from step 2 until no slice is left.

Rules:

- On the base branch (where the remote HEAD points), recommend a branch before the first test, named by the spec slug or a short slug of the one-sentence plan, and ask: working on the base branch is the user's call, never an assumption. A session already on a feature branch stays there.
- One implementation at a time. Unlanded work is never abandoned for a new task on your own: offer to finish and land it, land it partial, or park it, and let the user pick. Only `land` ends the work.
- No production code before its failing test exists, except wiring whose only effect lives in a host the tests cannot drive (a plugin entry point, a framework registration): its proof is an end-to-end run through `verify`, never a regex or string match over source.
- Before the first slice that adds a module or an exported type, settle its shape per [shape first](references/shape-first.md); the `not implemented` stubs that sketch commits carry no behavior, so they come before the failing tests that fill them.
- Before a slice's first test, list the ways it can fail. Test the likely and the costly ones (lost data, money, access, a broken caller contract) and name the rest in the commit message. Size tests to the change: a one-line fix gets one regression test, not new scaffolding.
- Inside a slice, run only the tests that exercise it, never the whole suite; the slice's gate waits for step 7, and `verify` decides its size. Inside a phase the spec declares, the gate follows [outcome-oriented execution](references/outcome-oriented-execution.md); a run of similar edits follows [sequence verifiable units](references/sequence-verifiable-units.md).
- A test that passes regardless of the change protects nothing ([test behavior, not implementation](references/test-behavior-not-implementation.md), opened when an assertion does not plainly compare the subject's output with a literal value); grep-style string checks counterfeit falsifiability. A slice whose tests never went red on the behavior under test is not done.
- Keep every diff surgical: each changed line traces to the slice, or to dead code removed from a file it changes.
- Before adding anything, walk the ladder: does it need to exist, does the stdlib or platform do it, does a present dependency, does one line. Before adding a file, a layer, a dependency, or a parameter, open [laziness protocol](references/laziness-protocol.md) and [subtract before you add](references/subtract-before-you-add.md); a wrapper, a layer, or a piece of state goes in only when it passes the test in [minimize reader load](references/minimize-reader-load.md). Test code walks the ladder too: extend the existing fake, fixture, or helper before writing a new one, as part of the slice.
- Mechanical work (a sweep of edits, a migration, generated files, an analysis over data) is done by a tool built for it: open [build the lever](references/build-the-lever.md) before the first hand edit.
- When a slice's logic holds state, branches on a shape, or lays down a type later slices share, the data shape comes first: open [model the domain](references/model-the-domain.md) and [foundational thinking](references/foundational-thinking.md) before writing that logic.
- Type-safe with no escape hatches ([type-system discipline](references/type-system-discipline.md), opened when designing a type or a signature). Defensive at I/O edges, trusting inside; configuration is input, validated where it is constructed and refused there, not on first use ([boundary discipline](references/boundary-discipline.md), opened when wiring validation, error handling, an adapter, or configuration). No silent fallback that hides failure.
- Every call across the network is bounded by a timeout, and a write a caller may retry carries an idempotency key ([make operations idempotent](references/make-operations-idempotent.md), opened for a command, startup step, scheduler, or loop that writes state and can run twice).
- When two operations touch the same record, run them one at a time, or claim the record before the `await` (mark it in progress) and re-check after it every condition read before it; a re-check alone lets a charge or a send run twice ([separate before serializing shared state](references/separate-before-serializing-shared-state.md), opened when two actors could write the same file, key, or record).
- A component's state changes only through its own operations: never hand out a reference to it that a caller could mutate or that changes under them ([minimize reader load](references/minimize-reader-load.md), opened before exposing a component's state).
- Delete what your change orphaned ([migrate callers, then delete legacy APIs](references/migrate-callers-then-delete-legacy-apis.md), opened before writing a new API that replaces one that still has callers). In the files the slice changes, delete dead code too, before adding to them: unused functions, imports, and parameters, branches no caller reaches, stale flags, validators that repeat a check an edge already made, and comments that restate the code or excuse a workaround, unless a non-goal fences them. Dead code in other files is flagged, not removed.
- Write no comment that restates the code or explains a workaround: fix the workaround at its cause, or hold the constraint in a type, a lint rule, or a test. A comment stays only for what the code cannot say, such as behavior outside the project's control (a browser quirk, a vendor bug, a protocol requirement).
- A slice that builds UI takes its type, color, and spacing from the project's `DESIGN.md` when one exists.
- Each slice's commit message is one line in the repository's convention (read recent `git log`; imperative lowercase when there is none), names the criterion by what it says, never its spec id, and gives the why, not only the what. Stage the specific files, never `git add .`.
- A bug or unexpected failure mid-slice routes to the `debug` skill; do not patch around symptoms.
- A genuine fork found mid-slice is never guessed: stop, name it, and let the user answer. A fork is genuine when it changes an acceptance criterion, a non-goal, or a public interface, needs the user's authority, or cannot be undone; any other fork that running something can settle is settled by running it, per [never block on the human](references/never-block-on-the-human.md).
- Three failed attempts on the same slice stop the loop: escalate to the user with the criterion, what was tried, and the last error.
- When the last slice lands, run `verify` before claiming the work is done, and `rubric` too when the work is a UI, a public interface, a name, or a doc, since the maker never judges its own taste.
