# Experience first

When what is easy to build conflicts with what serves the person using it, the person wins.

When: a trade-off on product scope, UX, or an interface pits implementation convenience against the consumer's experience.

- The consumer is whoever uses the work: the end user of a UI, the colleague who imports a library or internal API, and the engineer who maintains the code next. Weigh each of them the same way, and state a choice's impact in their terms.
- Every feature, control, and option earns its place.
- Fewer features done well beat more done roughly: three polished ones beat ten rough ones.
- Settle feel before committing, with the prototype skill when prose cannot, per step 5.
- Finish the details: transitions, alignment, spacing, feedback, and the error states.
- Keep the core loop tight: a feature serves the central workflow or stays out of its way.
- Foundations exist to serve the experience: implement's foundational-thinking principle orders the work, and this file sets what the work aims at.

Where it stops: the stated constraints decide what stays in the design; this file never adds a feature for delight, it sets the bar for what stays. Choosing among approaches is [exhaust the design space](exhaust-the-design-space.md).
