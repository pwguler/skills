# Experience first

When ease of building conflicts with what serves the user of the work, the user wins.

When: a trade-off on product scope, UX, or an interface puts ease of building against the consumer's experience.

- The consumer is each person who uses the work. That is the end user of a UI, and the colleague who imports your library or internal API. It is also the engineer who maintains the code next. Weigh each of them the same way. State the effect of a choice in their terms.
- Keep a feature, control, or option only when a named consumer's task fails or slows down without it.
- Ship a feature complete or not at all. Every action gives feedback, and every failure shows an error state. Transitions, alignment, and spacing match the rest of the UI. When the work cannot complete each feature this way, ship fewer features.
- Settle the feel before you commit to a design. Use the prototype skill when text cannot settle it, as step 5 says.
- A feature that does not serve the central workflow adds no step, prompt, or screen to it.

Where it stops: the stated constraints decide what stays in the design. This file never adds a feature only because it is pleasant. It sets the standard for what stays. To choose among approaches, use [exhaust the design space](exhaust-the-design-space.md). To order the work, use implement's foundational-thinking principle.
